# 泡泡潮 · 立体泡泡方案讨论

> 只读代码后的技术讨论稿，**未改动任何文件**。
> 现有实现：`BubbleTide.shader`（体积光线步进）+ `BubbleSDF.shader`（逐像素泡泡 SDF）

---

## 一、先说清楚现在的瓶颈在哪

现在有**两套**泡泡渲染，两套都是**逐像素光线步进**：

| 文件 | 做法 | 成本 |
|---|---|---|
| `BubbleTide.shader` | 全屏三角，每像素在 3D 纹理里步进，找泡泡壳面 | 128 步 × 每步 3 次纹理采样 + 法线要再加 6 次 |
| `BubbleSDF.shader` | 全屏三角，`SceneDistance` **循环遍历所有可见泡泡**，`Raymarch` 最多 128 步，每步再遍历一遍泡泡算保守步长 | 见下 |

`BubbleSDF` 那条路每像素的实际开销是：

```
每步：SceneDistance(p)              → N 次 BubbleShellDistance（含 sin 扰动）
    + 保守步长循环                    → 再 N 次
法线：SceneNormal → 4 × SceneDistance → 4N 次
        （差分离散步长必须 < 壳厚，所以这 4 次是硬成本，省不掉）
```

**大约 8N 次距离函数求值 / 每像素 / 每次采样。** N = 100 时是 800 次，
N = 5000 时是 4 万次 —— 一条 1080p 的 200 万像素屏幕就是 **800 亿次**。

**所以结论很直接：现在的 SDF 渲染器在 N 上有个硬墙（大约 100~500 颗），
和「几千颗泡泡填满地图」这件事在数量级上就不兼容。**
这不是调参能救的，O(N) 循环必须消失。

⚠️ 但要说清楚：**问题出在「逐像素 O(N)」，不是出在「场」这个概念上。**
`BubbleTideField` 那套「烤一张表 + 查表」的做法依然是对的，后面还要靠它。

## 二、为什么几千个 3D 物体只有一个可行解

一旦泡泡从「屏幕上一个场」变成「场景里 N 个实体」，你就只剩一条路：

> **让硬件深度缓冲去做重叠和遮挡。**

深度缓冲是唯一能在**不遍历所有泡泡**的前提下正确解算遮挡的机制。
它把「谁在前面」这个问题从 O(N²) 降到「硬件免费」。

所以方向是确定的：**Instancing + 深度测试**。
真正需要讨论的不是「要不要用」，而是**「怎么在几千个实例下活下来」**。

## 三、四种做法的成本对照

| # | 做法 | 每实例几何 | 遮挡 | 代价 | 适用规模 |
|---|---|---|---|---|---|
| A | 实例化球体网格 `DrawMeshInstanced` | 42~80 面 icosphere | 深度缓冲 | 顶点 + 填充率 | 屏幕内 500~2000 |
| B | 实例化四边形 + 解析光线-球求交 | 4 顶点 | 深度缓冲 | 几乎全是填充率 | 屏幕内 2000~10000（**推荐远中距离**） |
| C | 体积光线步进场（现状） | 1 个全屏三角 | 步进求交 | 与泡泡数无关，与像素数成正比 | 任意数量，但只适合**远景/雾化** |
| D | 现状 SDF 逐像素 O(N) 循环 | 1 个全屏三角 | 步进求交 | 8N / 像素 | **≤200，无法扩展** |

**推荐：A（近）+ B（中）+ C（远）三层 LOD，D 退役。**

## 四、先算清楚「泡泡预算」—— 这个数决定一切

房间 41.5 × 13 × 33.5 米 ≈ **18,000 立方米**。按 30% 体积被泡泡占据来算：

| 泡泡半径 | 单颗体积 | 铺满 30% 需要 | 评价 |
|---|---|---|---|
| 0.35 m（现在 field 用的值） | 0.18 m³ | **≈ 30,000 颗** | 几何方案不可能 |
| 0.5 m | 0.52 m³ | ≈ 10,400 颗 | 桌面勉强，手机不行 |
| 0.8 m | 2.1 m³ | ≈ 2,500 颗 | **几何方案合理区间** |
| 1.2 m | 7.2 m³ | ≈ 750 颗 | 舒服，但看起来像气球不像泡沫 |

> **关键结论：「用 0.35 米的泡泡铺满整张地图」= 三万颗，这条路在几何方案上是不通的。**
> 想要立体泡泡填满地图，**必须把泡泡做大**（0.8~1.2 米），或者接受「只有局部是真泡泡」。

这个数字要你先拍板，因为它决定了后面所有架构。

## 五、性能上的五个真正的坑（按严重程度）

### ⚠️ 坑 1：半透明堆叠的 overdraw —— 最大的杀手

一堆半透明泡泡叠在一起，每个屏幕像素会被**混合 5~20 次**。
手机上混合像素的吞吐量大概只有不透明像素的 1/4~1/8，这一下就差一个数量级。

**解法（这条能省最多）：**

不要画「一个半透明的实心球」，要画「**只有边缘可见的球壳**」：

```
泡泡的视觉本来就全在边缘：
  菲涅尔环 + 薄膜彩虹 + 掠射角高光
正对相机的球心区域本来就是接近全透明的

→ 只在 |N·V| 小的地方（边缘）产生高 alpha
→ 屏幕上的实际覆盖面积从 O(πr²) 降到 O(2πr·w)，能省 70%+
→ 再配合 dither 裁剪（alpha 转屏幕像素抖动），连混合都可以省掉
```

单个泡泡看起来依然是透明的（因为你能透过它看到后面的泡泡和场景），
但 GPU 那边的混合量掉了一个数量级。**性价比最高的一条。**

### ⚠️ 坑 2：别用顶点色/材质，用全局参数

几千个实例如果每个都要自己的材质属性，合批就废了。
所有泡泡走**同一个 shader + 同一套全局参数**，每颗的差异（相位、颜色微差）
用 `instanceID` 哈希算出来，不要传进来。

### ⚠️ 坑 3：不要每帧上传矩阵数组 ← 这个坑最容易踩

`DrawMeshInstanced` 要 `Matrix4x4[]`。泡泡是**持续变多**的，
所以你会忍不住每帧重建整个数组 —— 5000 颗就是每帧 **320 KB** 上传加一次全量矩阵计算。

**正确做法：把「填满」的进度做成一个 shader 参数，而不是改 CPU 端的数组。**

```
开局一次性烘好（和现在烤 Dijkstra 同一次）：
  StructuredBuffer：每颗泡泡的 { 位置, 半径, 出现时刻, 相位 }
  → 只上传一次，之后永不再传

每帧 CPU 只写一个 float：
  Shader.SetGlobalFloat("_BubbleTideReveal", progress);

vertex shader 里：
  slot = _BubbleInstanceBuffer[instanceID];
  appear = saturate((progress - slot.appearTime) / growDuration);
  if (appear <= 0) 输出退化三角形（直接丢掉）
  positionWS = slot.pos + objectSpacePos * (slot.radius * ease(appear));
```

**好处翻倍**：
- 每帧 CPU 开销 = 写 1 个 float，与泡泡数**完全无关**（5 万颗也一样）
- 出现动画免费拿到（从 0 长到满，自带「啵」的一下的观感）
- 因为不再改实例数，还能顺手按 `appearTime` 排序后二分，用 `instanceCount` 截断

**这是把「慢慢充满」做便宜的核心技巧，强烈建议就这么做。**

### ⚠️ 坑 4：LOD 过渡会「跳」

球 → 四边形 impostor 的切换必须有过渡，否则近处会看到明显的形变。
两个可选做法：
- 切换窗口内用**屏幕空间 dither 交叉淡化**（推荐，4 行代码）
- 或者干脆**远处不画几何**，交给雾效 + 场（C），让泡泡「化进雾里」

### ⚠️ 坑 5：别在这个方案里重新引入逐像素排序

一旦决定「mass 用不透明渲染」，就**完全不要碰透明排序**。
`Renderer` 的 sorting 是 O(n log n) 且会打断合批。
泡泡本身是透明的，但**用深度缓冲替代排序**才是这个方案能成立的原因。

## 六、和现有系统的衔接（好消息：基本不用动玩法）

**保留 `BubbleTideField` 的全部成果**，只是它从「渲染数据源」降级成「碰撞与时间数据源」：

| 现在由 field 负责 | 改完之后 |
|---|---|
| 玩家推挤方向 / 淹没判定 | **不变**，`SampleArrivalTime` / `SampleFlowDirection` 照用 |
| 截止时刻 `Deadline` / 宽限 | **不变** |
| 三种反制（炸洞 / 筑墙 / 抽容量） | **不变**，依然改的是那张时间表 |
| 潮水的**外观** | **换掉**：从 `BubbleTideCellRenderer` 改成发布泡泡实例 |

**具体改动面：**
- `BubbleTideCellRenderer`：不再写 `_BubbleTideElapsed`，改成写 `_BubbleTideReveal`
- 新增一个 `BubbleTideInstances`：开局从 field 生成泡泡布局，烘进一个 `ComputeBuffer`
- `BubbleTide.shader`：退役，或只留作超远景的雾状兜底

**泡泡布局直接从 field 生成，不要另外发明一套：**
field 里每个 `StateAir` 的格子都有「第几秒被淹」，
按 `bubbleSpacing` 抽稀 → 每颗泡泡的 `appearTime` = 该格子的 `arrivalTime`。
这样「泡泡填满地图的顺序」和你现在调好的潮水**天然一致**，
不用重新调一遍节奏。布局用现有的确定性哈希（`Hash01`），保证每次跑一样。

## 七、需要你拍板的几件事

1. **发布平台是什么？** PC / 手机 / 都要。
   这一条直接决定预算是一个数量级还是另一个数量级。
2. **屏幕里同时大概想看到多少颗？** 500 / 2000 / 10000。
   这个数决定 A 和 B 的切换点放在哪。
3. **泡泡做多大？** 这条最关键（见第四节）。
   0.35 米 → 三万颗，几何方案不通；0.8~1.2 米 → 750~2500 颗，可行。
4. **旧的 SDF 渲染怎么处理？** 退役 / 保留给超远景当雾。
   （`BubbleSettings.maxSize` 是 1.5 米直径，如果按这个走，预算落在 0.8 米半径附近，是合理的）
5. **「填满」是全场可见，还是镜头附近可见就行？**
   如果要全场，就必须有远距离兜底（B 或 C）；如果镜头附近够了，A+B 就收工。

## 八、我的建议（等你确认上面的问题）

**分三步走，每步都能单独出效果、单独回滚：**

1. **第一步（半天）**：写一个 `BubbleInstancedRenderer`，
   用一个 42 面 icosphere + 一个从 `BubbleSDF.shader` 抠出来的**单球**着色函数
   （菲涅尔 + 彩虹 + 双高光，但**去掉逐像素 O(N) 循环和 raymarch**），
   开 `DrawMeshInstanced`，位置和 `appearTime` 从 field 生成，用 `_BubbleTideReveal` 驱动出现。
   → 这一步就能看到「立体泡泡慢慢铺满地图」，而且成本可控。

2. **第二步（一天）**：按屏幕投影大小加四边形 impostor LOD（做法 B），
   把远处的几何量砍掉。加 42 面/80 面的 icosphere 资源。

3. **第三步（半天）**：边缘-only 着色 + dither，
   把 overdraw 压下去，然后上真机测。

**先不要做**：不要现在就上 GPU Instancing 的间接绘制（`RenderMeshIndirect`），
不要碰 Unity 的 GPU 剔除，不要在第一步就做排序。
这些在这个规模下都用不上，只会拖慢进度。

## 九、一句话

> **把「每个像素遍历所有泡泡」换成「每个泡泡只覆盖它那几十个像素」，
> 遮挡交给深度缓冲，数量交给 instancing，进度交给一个 float。**
>
> 剩下的唯一数学问题是：**泡泡得多大，才能用几千颗填满这 18,000 立方米。**
