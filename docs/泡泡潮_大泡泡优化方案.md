# 泡泡潮 · 大泡泡（5~10 米 / <100 颗）优化方案

> 只读代码后的技术讨论稿，**未改动任何文件**。
> 现有实现：`BubbleSDF.shader`（逐像素球体追踪）+ `SDFBubble.cs` / `BubblePayload.cs`

---

## 一、先重算一遍账：这个规模其实很适合 SDF

上一轮我按 0.35 米 / 三万颗算的，那套结论**不适用**。
按 5~10 米半径、不到 100 颗重算：

| 量 | 值 |
|---|---|
| 泡泡包围盒总尺寸 | 40 × 15 × 35 米 |
| 有泡区域占屏幕比例 | 约 30~60% |
| 光线穿过整个泡泡云的长度 | **约 40 米**（不是 `PAO_MAX_DIST` 的 200） |
| 关键性质 | 光线打到球壳就 `return`，所以**大部分光线走 1~3 米就停了** |

**第二个性质是最重要的**：泡泡又大又密，大部分像素的第一次命中在很近的地方。
所以「每像素成本」不是按 40 米算，而是按**第一次命中前的距离**算 —— 平均只有几米。

**结论：逐像素光线步进在这个规模下是可行的，而且是你现有观感的唯一保持方式。**
不需要换成实例化网格。**但必须做几个针对性优化，否则会在两个地方翻车。**

## 二、最大的问题：步进用的是「球壳距离」，这在薄壳大球上是灾难

看 `BubbleShellDistance` 的返回值：

```hlsl
float dist = max(dOuter, -dInner);   // 壳体中面的有符号距离
```

然后 `Raymarch` 里：

```hlsl
t += clamp(d, minThickness * 0.3, maxStep);
```

**问题在这**：一个半径 5~10 米的泡泡，膜厚 `shellRatio` 是 0.06，
于是壳体厚度约 0.3~0.6 米。你在壳体附近时 `dist` 很小，
而最小步长被夹在 `minThickness * 0.3`，**每步只能挪几厘米到十几厘米**。

一条 40 米的光线要几十上百步，而 `PAO_MAX_STEP` 只有 128 ——
**步数会在半路耗尽，表现为泡泡表面被硬切一刀**（shader 里 `marched < 0.5`
那一段就是在给这个打补丁，`alpha *= 0.30`，但那只是遮丑）。

### 解法：步进用「整球距离」，只在最后几米切到壳体距离

球壳是**极薄**的，所以球体内部 99% 的体积其实是空的，可以一跳而过。

```hlsl
// 每步都算两个值：
float dShell = SceneDistance(p);          // 精确：到壳体中面（保留求交用）
float dBall  = SceneBallDistance(p);      // 便宜：到最近整球表面（用来走路）

// 走路用整球距离 —— 大球内部能一次跳几十米
// 只在离壳足够近时才退回壳体距离，保证不漏掉 0.3 米厚的膜
float marchDist = (dBall < minThickness * 4.0)
                ? dShell
                : max(dBall - minThickness, 0.0);

t += clamp(marchDist, minThickness * 0.25, maxStep);
```

- `SceneBallDistance` 里**不要**有 `sin`、**不要**有 `exp`、**不要**有 `smin`
  —— 就是纯 `length(p - c) - R` 取最小，快得离谱
- 这一步通常能把步数从「上百步耗尽」压到 **10~30 步**，是最值钱的单点优化

## 三、其余六个该做的优化（按性价比排序）

### 1. 包围球剔除 —— 现在每步都在遍历全部 100 颗

`SceneDistance` 里 `for (i < _ShapeDataCount)` 对每颗都算一遍完整距离函数。
但一条光线每步只会靠近其中 2~5 颗。

```hlsl
for (int i = 0; i < _ShapeDataCount; ++i) {
    float4 s = _ShapeDataBuffer[i];
    float R = s.sizeOp.x * 0.5;

    // 到整球表面的距离 —— 一个 length 就能判掉绝大多数
    float3 q = p - s.posType.xyz;
    float ballDist = length(q) - R;

    // 这颗球离得太远，对距离场没有贡献（远场 smin 退化成 min）
    if (ballDist > fuseMax) continue;

    // 只有真正在附近的才做完整计算（含 sin 扰动）
    d = smin(d, BubbleShellDistance(s, p), k);
}
```

`BubbleShellDistance` 里那三个 `sin` 是真贵，而它们只在
`abs(dist) < radius * 1.1` 时才生效 —— 大部分时候白算。
**先剔除、再算**，这一条能把每步成本砍掉一个数量级。

### 2. 只在场内步进 + 场外提前退出

现在是 `PAO_MAX_DIST = 200.0`，但泡泡包围盒只有 40 米。
开场先做一次光线-AABB 求交（`BubbleTide.shader` 里已经有现成的 `RayBoxEntry` 可以抄）：

```hlsl
float tEnter, tExit;
if (!RayBoxIntersect(rayPos, rayDir, clusterMin, clusterMax, tEnter, tExit))
    return half4(0,0,0,0);        // 整条光线都不进泡泡云 —— 一个像素的成本

float t = max(tEnter, 0.0);
float tMax = min(tExit, maxDistance);   // 不再用 200
```

**绝大多数像素（天、地、墙）会在这里直接返回。**

### 3. 命中后「跳过大球内部」而不是慢慢走

一旦 `dBall` 说明在某颗球内部，可以直接跳到这颗球的出射点：

```hlsl
// 已经进到某颗球里了 → 直接跳到它的远交点，中间全空
float farHit = RaySphereFar(p, rayDir, nearestCenter, R);
if (farHit > 0) t = max(t, farHit - minThickness);
```

这是把「斜穿一个大泡泡」从几百步压到一步的关键。

### 4. `Raymarch` 里那个「每步再遍历一遍所有球」的循环可以删掉

现在的 `Raymarch` 里有这么一段：

```hlsl
float minSurf = 1e9;
for (int j = 0; j < _ShapeDataCount; ++j) { ... }   // 每步再来一遍 N
```

它只是为了算「要不要缩小步长」。但你在第二节优化完之后，
`SceneBallDistance` 返回的 `dBall` **本身就是** `minSurf`。
**同一个循环做了两遍**，删掉第二个，直接省一半。

### 5. `SceneMinThickness` 每帧每像素都在遍历

```hlsl
float SceneMinThickness() { for (i...) mn = min(mn, ...); }
```

这个值**只和泡泡参数有关，和像素无关**。
放到 C# 里算一次，`SetGlobalFloat` 传进来。白捡的。

### 6. 法线的四次求值要复用

```hlsl
float3 SceneNormal(float3 p, float eps) {
    n.x = SceneDistance(p + e.xyy) - SceneDistance(p - e.xyy);   // 4 次全场景求值
    ...
}
```

法线是硬成本（差分离散步长必须 < 壳厚），但可以：
- 复用 `Raymarch` 循环里已经算过的中心点距离
- 或者改成 3 次前向差分（少一次 `SceneDistance`），卡通风格下精度完全够

## 四、卡通风格其实让你更省钱，不是更贵

这一点值得单独说：**「卡通」和「便宜」在这个方案里是同向的。**

`BubbleShellDistance` 里那段逐像素正弦扰动，对写实泡泡是加分项，
但**卡通风格要的是形状稳定、边缘干净**，不是表面毛毛躁躁。

```hlsl
float wob = sin(tt*1.00 + nb.x*w*12.9898)
          * sin(tt*1.31 + nb.y*w*7.2330)
          * sin(tt*0.77 + nb.z*w*9.5170);      // 3 次 sin / 每颗 / 每步
```

三个选择，按推荐顺序：

1. **把扰动降到很低频，或干脆关掉** —— 卡通泡泡本来就该是干净的球形轮廓，
   现在是 `m_Distortion = 0.08`。**这一条能省掉大部分 `sin`**
2. **用便宜的近似代替 `sin`**，比如 `wob = t*(1-t)` 那种抛物线型
3. **把扰动烘进顶点**，如果哪天换成网格方案（这一轮不需要）

另外两处也是同一个道理：

| 现在 | 卡通做法 |
|---|---|
| `exp2(-abs(di) * 6.0)` 算权重（`WeightAt`，每颗都要算） | 用**带状**（`smoothstep` 的分段）代替，卡通本来就要硬边 |
| `SceneColor` / `SceneShapeAlpha` 又遍历一遍所有球 | 命中点的颜色在 `SceneDistance` 循环里顺手带出来，**别再遍历第三遍** |

> **命中点的循环已经跑了 5 遍（距离、法线×4、颜色、alpha）。**
> 理清之后应该只剩「距离 + 法线」，这是 2~3 倍的差距。

**卡通还有一件几乎免费的事：轮廓线。**
真实泡泡没有轮廓，但卡通泡泡必须有那一圈边。
你 shader 里 `fresnel = pow(1 - NoV, _BubbleRimPower)` 已经是轮廓了，
只要加一个「`NoV` 低于阈值就压暗 / 上色」的形态，就是标准卡通描边，成本为零。
**大泡泡 + 明确的轮廓线 = 卡通感的主要来源**，比彩虹和高光重要。

## 五、真正的风险：相机跑到泡泡里面

这是唯一能让这套方案「看起来坏掉」的情况，而且你的游戏里**真的会发生**
（`BubbleRideInteractor` 允许玩家钻进泡泡开着走）。

一旦相机在 5~10 米的大泡泡内部：
- 到壳体的距离只有 0.3 米，最小步长被夹住 → 步数瞬间耗尽
- 屏幕上会出现硬切的边、或者整个屏幕糊成一片
- 视角一动就是满屏噪点

**三个应对，建议全做：**

1. **相机在球内时，把该球从距离场里摘掉**（或者把它的壳翻面渲染）
   —— C# 每帧判断一次 `length(camPos - center) < R`，把结果写进
   `Payload` 的一个 flag 位，shader 里 `if (s.pad0 > 0.5) continue;`
   **这是最稳的做法，成本几乎为零。**
2. **加一个「镜头最近距离」保护**：相机离任何球面小于 0.5 米时，
   强制把它推出去（类似 `PlayerController` 已有的相机防穿墙逻辑）
3. **内部渲染单独处理**：进泡泡时切到你已有的 `UnderwaterFullscreen` 那套全屏效果，
   不要指望 SDF 在内部还能正确出图

## 六、平台问题：桌面可以，手机不行

粗算（1080p，2M 像素，优化后）：

| | 每像素求值次数 | 全屏求值 | 评价 |
|---|---|---|---|
| 优化前 | 约 2000+ | 40 亿+ | 桌面勉强，手机必死 |
| 优化后（第 2、3 节全做） | 约 300~800 | 6~16 亿 | **桌面流畅，手机仍然吃力** |

手机上还想跑的话，只有一条路：**半分辨率出 SDF，再上采样**
（`BubbleSDFRenderFeature` 现在已经有降采样的能力，注释里提到了）。
4 倍填充率收益，代价是边缘变糊 —— 但**卡通风格对糊的容忍度比其他风格高得多**，
因为卡通本来就靠轮廓和色块，不靠细节。

**所以：如果是手机发行，半分辨率几乎是必选项，而且和卡通风格不冲突。**

## 七、要不要换成实例化网格？—— 这一轮不用

上一轮我推实例化网格，那是针对「几千颗」的。**这个规模下不划算**，因为：

| 你现有观感里最值钱的东西 | 光线步进 | 实例化网格 |
|---|---|---|
| 泡泡之间**融球式平滑并集**（`smin`） | 天然就有 | **做不到**，只能看到硬相交的边 |
| 薄壳的菲涅尔 + 薄膜彩虹 | 现成的 | 要重写一套 |
| 形状可以逐帧变 | 改数据就行 | 要重烘焙网格 |
| 遮挡正确性 | 需要步进求交 | 深度缓冲免费 |

`SDFBubble.FuseStrength` 默认 0.22 —— **你现在的泡泡是会互相融合的**，
这是「一团泡泡挤在一起」这个观感的核心。换成网格就没了。

**所以：保留光线步进，做第二到四节的优化。** 那是 1~2 天的工作量，
换回 10~50 倍的性能，而且观感一分不丢。

**什么时候才该换网格：** 泡泡数上到 500 以上，或者要发行手机并且
半分辨率也压不住。那时再换，现在不用提前还债。

## 八、建议的动手顺序

| 步骤 | 内容 | 预期收益 | 工作量 |
|---|---|---|---|
| 1 | 步进改用「整球距离」（第二节） | 步数 5~10 倍下降，**救命级** | 2 小时 |
| 2 | 包围球剔除 + 删掉 `Raymarch` 里重复的 N 循环 | 每步成本 5~10 倍下降 | 2 小时 |
| 3 | 光线-AABB 求交 + `tMax` 收进包围盒 | 场外像素几乎免费 | 1 小时 |
| 4 | `SceneMinThickness` 挪到 C# | 白捡 | 15 分钟 |
| 5 | 相机在球内时摘掉该球（第五节） | **修掉唯一的致命 bug** | 1 小时 |
| 6 | 收敛那 5 遍循环 → 2 遍；权重改带状 | 再 2 倍 | 半天 |
| 7 | 卡通描边 + 关掉高频扰动 | 观感 + 再省一批 `sin` | 半天 |
| 8 | （手机才需要）半分辨率 SDF | 4 倍填充率 | 半天 |

**1~5 步做完就能上真机测了**，大约一天。做完再决定要不要继续往下。

## 九、一句话

> **你的方案没选错 —— 5~10 米、100 颗以内正是光线步进的甜区。**
>
> 唯一的结构性问题是**步进用了 0.3 米厚的球壳距离去走 40 米的空间**，
> 128 步根本不够。改成「整球距离走路、临门一脚才切壳体距离」，
> 再把包围球剔除和场外退出补上，就是 10~50 倍。
>
> 真正会翻车的只有一件事：**相机钻进泡泡里面**。那个必须单独处理。
